01 / Architecture

Weaving measurement concerns

scripts/weave.py validates one or more TOML aspect files, generates C code specialized to their declarations, and compiles it with the shared runtime and specified device code. It reports and skips aspects that cannot be built; invalid configuration or a failure of the compiler or shared runtime remains an error. This is aspect-oriented composition of measurement concerns: the workload is run as a separate command, not rewritten or instrumented by the weaver.

INPUT

TOML + device code

Metric aspects with readers, and separate powercap control aspects.

GENERATED

Aspect code + glue

Sampling code for metrics and hooks for controls, plus registration and flags.

LINKED

Executable

Shared runtime and declared libraries coordinate the workload and output.

In over-time mode each aspect has one sampling thread for its selected metrics; powercap control aspects have none. Aggregate mode uses no sampling threads and generates no additional modules: aspects are woven into the main module. The source of truth for the runtime contract is gm_aspect.h.

02 / TOML

Read a configuration

Each TOML file declares at most one aspect through [measurement], [device] and [[metric]] tables. A metric supplies one CSV column; a powercap control aspect supplies hooks without metrics. The old [[aspect]] format is rejected.

[measurement]
aspect = "NvidiaGPU"
mode = "over-time"
setup = "int nvidia_begin()"
teardown = "void nvidia_end()"

[device]
lib = "../../src/devices/libgm_nvidia_gpu.a"
header = "../../src/devices/linux/gpu/nvidia/nvidia_gpu.h"
link = ["-lnvidia-ml"]

[[metric]]
name = "NvidiaGPU.Energy"
measurement = "double nvidia_get_energy()"
kind = "counter"
unit = "J"

This declaration produces --NvidiaGPU.Energy and NvidiaGPU.Energy_J. Library paths are relative to the TOML; workload, output and baseline paths are relative to the runtime working directory. Reweave after editing a declaration.

03 / Invocation

Runtime options

The measurement mode (aggregate or over-time) is woven into the executable; --temperature-calibration and --powercap-calibration remain runtime flags. Select metrics by their flags; none are selected automatically. --no-metrics can be combined with a powercap control flag. With no aspects selected, use -command alone.

OptionMeaning
-command, -program, -outputRequired workload command, CSV label and output path for measurement and powercap calibration.
-n_times, -sleep-secsRequired repetition count and pause; temperature calibration requires its settling time.
-powercap, -timeout-hoursComma-separated limits, required only with a selected powercap control; timeout is required, in hours, with 0 meaning unlimited.
-interval-msRequired sampling interval for over-time mode.
-temperature-control METRIC, -calib-file METRIC=PATH, -varianceRepeat the control option and supply a separate file for each controlled sensor; variance is required when control is enabled. Control is independent of metric selection.
-range MIN-MAX, -compile_cmdRequired watt range and optional compilation command for powercap calibration.

Use --help on the generated executable. Missing baselines for available controlled sensors are calibrated and invalid files cause an error. An unavailable controlled temperature disables its thermal control with a warning; explicit temperature calibration fails.

04 / Field reference

[measurement] and [device]

Each file declares one metric aspect or one powercap control. At most 64 aspects can be woven, each with at most 64 metrics; help is a reserved name. All woven metric aspects must declare the same mode. With no active aspects, the executable runs the supplied -command using system() (optionally repeated with -n_times), without a CSV or timeout.

FieldContract
measurement.aspectRequired unique aspect name, made of identifiers separated by dots; it names the generated module and a control aspect's flag.
measurement.mode"aggregate" or "over-time"; required for metric aspects and woven into the executable.
device.header, device.lib, device.linkRequired header path; optional C source, object or library, and additional -l/-L flags. Paths are relative to the TOML. An aspect with missing or unbuildable dependencies is skipped with a warning.
measurement_start, measurement_stopPaired no-argument workload boundary callbacks, required for duration metrics; int or void.
setup, teardownOptional no-argument lifecycle functions. Aspects sharing setup must share teardown; initialization is performed once. A failed setup removes the affected aspect with a warning; required calibration fails.
powercap_set, powercap_restore, powercap_calibrationDeclare on a separate control aspect without metrics; set and restore must be declared together.

05 / Metric semantics

[[metric]]

Each [[metric]] declares a unique dotted name (its flag and CSV column), a no-argument numeric measurement function, an optional kind (counter, gauge or duration), an optional unit suffix and an optional thermal = true marker for a Celsius temperature gauge (at most one per aspect, with a required library calibration function that sleeps and returns the baseline). Aggregate mode reports counter differences and final gauge or duration readings; over-time records sampled readings. Execution time appears only when a duration aspect is selected. Time.WallClock is an optional example using CLOCK_MONOTONIC; Timestamp_ms remains the over-time axis. Negative and non-finite readings are ERROR. Thermal control only applies to sensors explicitly selected with -temperature-control.

06 / Hooks

Optional aspect hooks

Setup and teardown use no-argument void or int signatures. Powercap hooks use int set(int), int restore() and the GmCalibratePowercapFn signature in gm_aspect.h. The runtime exposes runTesting() to calibration implementations. Intel powercap has a separate library: omit the aspect to omit its implementation and dependencies, or leave it unselected to avoid changing limits at runtime.

07 / Extend

Bring your own device code

  1. Implement numeric C readers and expose them in a header.
  2. Declare one aspect per library with a [[metric]] per reader, marking temperature gauges with thermal = true.
  3. Declare lifecycle hooks and any separate powercap control aspect, weave and inspect the generated flags with --help.

The existing device libraries are optional examples. gm_workload_pid is available to workload-scoped readers.
