How it fits together

Each compiled plugin exports an energy_backend_descriptor containing its CPU or GPU backend and detection priority. The engine selects the highest-priority detected backend independently for each category. It then uses callbacks and metric definitions to read values.

The interface lives in energy-backend.h ↗. The metric catalogue maps each built-in metric to its reading function.

Backend callbacks

Both CpuBackend and GpuBackend share the callbacks below. A device is the core or device index supplied by the engine.

CallbackRequired?Responsibility
detect(void)YesReturn 1 if this backend can operate on the host. A backend that does not return 1 is not selected.
init(int device)YesInitialize resources for readings. Return 0 on success; report failure with a nonzero result.
cleanup(void)NoRelease resources at shutdown when provided.
sample_start(int device)YesCapture the beginning of a measurement window; return 0 on success.
sample_stop(int device)YesCapture the end of the window; return 0 on success.
get_metric(size_t index, int device, pid_t pid)YesReturn the indexed metric reading, or METRIC_NOT_SUPPORTED if unavailable. Process-scoped readings use the supplied PID.
diagnose(void)NoReturn a short explanation when detection fails.
set_powercap(int watts)CPU only; optionalApply a supported cap. The calling code treats -1 as leaving existing limits unchanged.
destroy_powercap(void)CPU only; optionalRelease or restore the active powercap context; the Intel implementation attempts to restore its saved limits.
calibrate_powercap(...)CPU only; optionalRun the backend's powercap sweep and return success or failure.

metrics and metric_count describe the indexed metrics; they are fields, not callbacks. CPU backends must supply a readable metric marked ENERGY_METRIC_FLAG_CPU_TEMPERATURE for measurements to run.

Define a metric

Built-in backends put an array of EnergyMetricDefinition near the top of their source. Each entry connects a descriptor, function and descriptive information. Declare the function before the array and implement it below:

static double read_load(int device, pid_t pid);

static const EnergyMetricDefinition backend_metric_definitions[] = {
    {
        .descriptor = {
            .name = "Load",
            .unit = "units",
            .kind = ENERGY_METRIC_GAUGE,
            .scope = ENERGY_METRIC_DEVICE,
            .flags = ENERGY_METRIC_FLAG_NONE
        },
        .function = ENERGY_METRIC_FUNCTION(read_load),
        .info = {
            .description = "Device load",
            .origin = "Hardware API"
        }
    }
};
ENERGY_DEFINE_METRIC_TABLE(backend, backend_metric_definitions)

static double read_load(int device, pid_t pid) {
    (void)device;
    (void)pid;
    return METRIC_NOT_SUPPORTED; /* Replace with a hardware read. */
}

In an existing backend, add an entry to its existing array; do not add a second table macro. The macro prepares the plugin's descriptor, function map, metadata and indexed getter. Choose window, gauge or peak semantics and device or process scope to match the actual reading. Use the corresponding CPU or GPU temperature flag only for a real temperature sensor.

The older ENERGY_DEFINE_METRICS macro remains available to existing plugins. Keep native plugin sources trusted: loading a library can execute its constructors.

Add a backend

  1. Copy the CPU or GPU template .c and .h into a new directory under src/platform/linux/cpu/ or gpu/.
  2. Implement hardware detection, initialization, sampling and the metric functions. The templates are placeholders and do not detect hardware or return real readings.
  3. Update the metric array, descriptor name and priority. For a CPU backend, provide a CPU temperature reading.
  4. Run make -C src and ./src/main --list-metrics cpu <directory> (or gpu). Verify actual hardware readings, units, errors and counter wraparound.

The build discovers a primary .c per backend directory. Extra sources, compiler flags and libraries are configured in src/Makefile; the Intel GPU links its separate sensors.c there.

External metric adapters

An external adapter is a separate shared library, not a CPU/GPU backend. Its greenmeasurer_metric_adapter descriptor uses init, read(index, value) and cleanup callbacks; it describes metrics by name and unit. See metric-adapter.h and the repository guide for configuration and source metrics.
