Measurement guide

Declare the measurement aspects you need, generate an executable and run your experiment.

01 / Setup

Generate, then run

Use Linux, a C compiler and Python 3.11 or Python with tomli. Optional device libraries have their own development dependencies; the build skips libraries whose required headers are missing. See the repository README for requirements.

make -C src
python3 scripts/weave.py examples/aggregate/system.toml examples/aggregate/time.toml \
  -o generated-experiment
./generated-experiment/greenmeasurer --help
./generated-experiment/greenmeasurer \
  -command "true" -program true -output result.csv \
  -n_times 1 -sleep-secs 0 -timeout-hours 0 --Time.WallClock --System.Cores

Generation compiles the executable but does not execute the workload. Missing dependencies or aspect build failures are reported and the affected aspects are skipped; use --help to see available flags. Without -o, the output is generated-<first config name> alongside that TOML. Runtime hardware access may require additional permissions.

02 / Configuration

Compose the aspects

Each TOML file declares one aspect: a [measurement] table with the aspect name, mode and lifecycle hooks, a [device] table with the library and header, and one [[metric]] per measured value. A separate powercap aspect declares control hooks and no metrics. A failed setup emits a warning and removes that aspect from the run. Explicit calibration fails if its required aspect is unavailable.

[measurement]
aspect = "System"
mode = "aggregate"

[device]
lib = "../../src/devices/libgm_system.a"
header = "../../src/devices/linux/system.h"

[[metric]]
name = "System.Cores"
measurement = "double system_get_core_count()"
kind = "gauge"
unit = "cores"

Paths in the TOML are relative to that TOML; workload, output and baseline paths are relative to the working directory. Reweave after changing a TOML. The mode is woven into the executable; pass the command, repetitions, output and other execution options when running it.

Select metric aspects explicitly with flags such as --System.Cores, or use --no-metrics. Powercap control has its own flag and can be selected with --no-metrics. Thermal control is selected separately from temperature metrics. With no active aspects, the executable runs -command using system() (optionally repeated with -n_times), without a CSV or timeout.

For adaptable configurations, see the per-aspect files in the aggregate/ and over-time/ folders of examples/; weave together the files you need. The NVIDIA and system examples do not depend on Intel libraries. Temperature calibration does not run the workload. For an explanation of every TOML field, see the configuration reference.

03 / Measure

Aggregate and over-time

The mode is declared in the aspect TOML and fixed at weave time. In aggregate mode, aspects remain active without sampling threads. Execution time appears only if a duration metric such as --Time.WallClock is selected. Counter metrics are reported as end minus start; gauges and durations use their final reading. In over-time mode, each aspect gets one sampling thread that samples its selected metrics. Powercap control has no sampling thread or metric column. Readers from the same header are serialized; libraries used through different headers must support concurrent reads. The CSV always aligns samples on a common Timestamp_ms grid; counters are raw readings.

Pass -interval-ms for over-time sampling, -n_times for repetitions and -sleep-secs for pauses. The interval is a target, not a guarantee of exact timing. Output appends to the CSV only when its header matches the selected aspects and mode.

Each workload execution, including a new powercap, starts with empty sampling buffers. The runtime stores the values returned by the readers without resetting counters or subtracting a baseline; a reader's cumulative value may therefore continue across powercaps. A grid row before a metric's first sample is available uses ERROR.

Timestamp_ms is the output time axis, while the optional Time.WallClock_ms is the wall-clock time measured by that aspect, including process startup and waiting, not CPU time. The timestamp origin is recorded before the aspect starts, and the final timestamp can include processing or the last sample after it stops. Sampling and grid alignment can also cause differences or repeated readings, so the timestamp can be larger even on the final row.

The generator's --max-samples sets the per-metric capacity at compile time. Exceeding it aborts the measurement. See interpreting results for unavailable values and scope.

04 / Calibrate

Temperature baseline

Mark temperature metrics with thermal = true (at most one per aspect) and declare the library's calibration function, which sleeps for the stabilization time and returns the baseline temperature. Intel CPU temperature has its own library and libsensors dependency; Intel energy metrics do not require it. Select each temperature explicitly and supply a separate -calib-file METRIC=PATH. --temperature-calibration waits -sleep-secs and overwrites each specified baseline with one reading; it does not run the workload.

Temperature metrics are informational unless control is selected separately with -temperature-control METRIC. Repeat it for each controlled sensor and provide its -calib-file METRIC=PATH and a shared -variance. A controlled sensor need not be selected as a metric. Before each run, every available controlled temperature must be at most its own baseline plus that variance. Missing files are calibrated first; invalid files for available sensors fail the run. An unavailable controlled sensor disables its own control with a warning; other available sensors remain controlled. Explicit temperature calibration fails if a selected sensor is unavailable.

05 / Control

Power limits and calibration

Select a declared control aspect such as --IntelCPU.Powercap and pass the required -powercap as a comma-separated list in watts. Without a selected control, omit -powercap; limits are unchanged and the CSV uses -1. The Intel control has its own library and dependencies; without the aspect they are not linked. Positive limits require paired powercap_set and powercap_restore hooks. With the Intel control selected, -1 applies the saved per-machine baseline. Select at most one powercap control aspect.

The Intel implementation stores the RAPL package/die limits and enabled state in /var/lib/greenmeasurer/intel-rapl-baseline. When powercap is first used, it loads that file or, if missing, saves the current state before changing limits. This happens during powercap setup, not ordinary aspect initialization; the saved state is not necessarily a factory or boot-time default.

--powercap-calibration requires an explicitly selected powercap aspect with a calibration hook and a runtime -range MIN-MAX. The supplied Intel implementation measures the baseline and each integer watt value in that range, and the report records the optimal powercap (lowest package energy) in a text file next to the CSV for later measurements. Optional -compile_cmd compiles the workload first.

Use with care

Powercap operations alter hardware limits and may require privileges. Review the range, output paths and device requirements before running. Calibration may replace its output file.

Troubleshooting

  • If generation fails, check TOML syntax, declarations, paths relative to the TOML, and whether required libraries were built.
  • If a reading is unavailable, check hardware, drivers and permissions.
  • For each controlled temperature, check its sensor and separate baseline file.
  • Run the executable with --help to see its options and aspect flags.
