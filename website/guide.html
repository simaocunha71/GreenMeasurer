Measurement guide

Declare the measurement aspects you need, generate an executable and run your experiment.

01 / Setup

Generate, then run

Use Linux, a C compiler and Python 3.11 or Python with tomli. Optional device libraries have their own development dependencies; the build skips libraries whose required headers are missing. See the repository README for requirements.

make -C src
python3 scripts/weave.py config.toml -o generated-experiment
./generated-experiment/greenmeasurer --help
./generated-experiment/greenmeasurer

Run these commands from the repository root with a standard or over-time configuration. Generation compiles the executable but does not execute the workload. Without -o, the output is generated-<config name> alongside the TOML. Runtime hardware access may require additional permissions.

02 / Configuration

Compose the aspects

[measurement] describes the mode and experiment. Each [[aspect]] declares a header and optionally a library, setup and teardown functions, and control hooks. Each aspect must declare at least one [[aspect.metric]], with a reader function and an optional kind and unit. Set optional = true to continue if an aspect fails setup: its selected columns remain in the CSV as NOT_SUPPORTED, with a warning and its hooks disabled. Its build dependencies are still required.

[measurement]
mode = "standard"
calibration_file = "temperature-baseline.txt"
command = "python3 my_program.py"
language = "Python"
program = "example"
output = "measurements.csv"

[[aspect]]
name = "System"
header = "../src/devices/linux/system.h"
lib = "../src/devices/libgm_system.a"

[[aspect.metric]]
name = "Cores"
read = "double system_get_core_count()"
kind = "gauge"
unit = "cores"

This example assumes the TOML is in a directory immediately under the repository root and that my_program.py exists in the root. Device paths resolve relative to the TOML; workload commands and output paths resolve from the directory in which the generated executable is run. Reweave after changing the TOML.

Every configuration must set a non-empty calibration_file path in [measurement]. There is no default temperature-baseline path; choose the same path in configurations that should share a baseline.

Only declared metrics exist in the generated executable. With no metric flags, declared metrics are selected by default; passing metric flags such as --System.Cores selects those flags instead. --no-metrics selects none, but does not necessarily disable thermal or powercap hooks. If the TOML declares no aspects, the generated executable instead calls system(command) once: no CSV, timeout or command-line overrides are available. Only mode, calibration_file and command may be specified.

For adaptable Fibonacci configurations, see the combined TOMLs and the intel/, nvidia/ and system/ folders in examples/. The NVIDIA and system calibration examples use Intel CPU hooks; temperature calibration does not run the workload. For an explanation of every TOML field, see the configuration reference.

03 / Measure

Standard and over-time

In standard mode, aspects remain active without sampling threads, and each run produces a row with Time_ms. Counter metrics are reported as end minus start; gauges use their final reading. In over-time mode, the runtime starts one sampling thread per active aspect through functions generated in its <Aspect>.c file. The CSV aligns samples on a common Timestamp_ms grid and retains a final row; counters are raw readings, not per-interval energy or power.

Set interval_ms for over-time sampling, and repetitions and sleep_seconds for repeated runs and pauses. The interval is a target, not a guarantee of exact timing. Standard and over-time output append to the configured CSV; use separate files when changing the selected metrics or experiment schema.

The generator's --max-samples sets the per-metric capacity at compile time. Exceeding it aborts the measurement. See interpreting results for unavailable values and scope.

04 / Calibrate

Temperature baseline

temperature-calibration requires an aspect with a thermal hook. It waits sleep_seconds, takes one reading, then overwrites calibration_file with a sensors snapshot and an Average temperature: ... line. It does not run the workload or calculate an average over the waiting period. The Intel CPU hook averages the current core temperature readings. A failed snapshot is reported as a warning.

For other modes, a configured thermal hook enables a wait before each run until the temperature is at most the baseline plus variance. If the explicitly configured baseline file is missing, it is calibrated first and written to that path. Without a thermal hook, there is no thermal control.

05 / Control

Power limits and calibration

Standard and over-time configurations may specify powercap as a value or list in watts. Positive limits require paired powercap_set and powercap_restore hooks. For the Intel CPU implementation, -1 applies the saved per-machine baseline; the runtime restores limits after measurement.

The Intel implementation stores the RAPL package/die limits and enabled state in /var/lib/greenmeasurer/intel-rapl-baseline. When powercap is first used, it loads that file or, if missing, saves the current state before changing limits. This happens during powercap setup, not ordinary aspect initialization; the saved state is not necessarily a factory or boot-time default.

powercap-calibration requires a calibration hook and powercap_min and powercap_max. The supplied Intel implementation measures the saved baseline and each integer watt value in that range, then merges the results. An optional compile_command can compile the workload before the sweep. Executables generated for this mode do not accept command-line arguments; change the TOML and regenerate to adjust the experiment.

Use with care

Powercap operations alter hardware limits and may require privileges. Review the range, output paths and device requirements before running. Calibration may replace its output file.

Troubleshooting

  • If generation fails, check TOML syntax, declarations, paths relative to the TOML, and whether required libraries were built.
  • If a device cannot initialize or a reading is unavailable, check the device's hardware, drivers and permissions. Not all counters are present on every machine.
  • If temperature control is configured, make sure its sensor and baseline file are accessible. The sensors command is needed for the snapshot.
  • Except for configured powercap-calibration executables, run the generated executable with --help to see its supported options and metric flags.
