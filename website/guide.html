Getting started

Install & build

GreenMeasurer currently targets Linux. You need a C compiler, Make and Python 3.11 or Python with tomli. Hardware backends have optional dependencies: Intel CPU uses powercap and raplcap; NVIDIA uses NVML. Read scripts/install.sh before using it to install dependencies.

git clone https://github.com/simaocunha71/GreenMeasurer.git
cd GreenMeasurer
make -C src VERBOSE=1
./src/main --list-metrics

The verbose build explains which optional backends were skipped. Intel RAPL MSR access may require loading the msr kernel module and elevated permissions. A built backend is not a guarantee that its hardware or every metric is available.

Make your first measurement

Edit configuration.toml in the repository root. Replace the placeholder command with your program:

[measurement]
mode = "standard"
command = "sleep 1"
language = "Shell"
program = "my-program"
output = "measurements.csv"
repetitions = 3
sleep_seconds = 0
powercap = -1

[metrics]
select = ["system.cores", "cpu.Package"]

Generate into a directory that does not already exist, then run the executable separately from the repository root:

./src/main --directory my-build
./my-build/greenmeasurer

Use ./src/main --config path/to/file.toml --directory my-build for a different file. Generation compiles but does not execute the workload. The executable embeds the configuration: after editing the TOML, generate again in a new directory. A successful measurement replaces its configured CSV.

For a complete example of using GreenMeasurer, follow the usage walkthrough from a sample program through standard and over-time CSVs. Ready-made test configurations are in configurations/; run their executables from the repository root so shared relative paths resolve as intended.

Choose a mode

ModeWhat it doesResult
standardRuns the command once per repetition; waits for the temperature threshold before each run.A CSV row per repetition and powercap value.
overtime (over-time)Runs the command once and samples while it executes; gates the start on temperature.A CSV row per sampling cycle.
temperature-calibrationWaits for the settling period and records a CPU temperature baseline.A text file with an lm-sensors snapshot and average temperature.
powercap-calibrationRuns a baseline and repeats the workload across an inclusive Watt range.A calibration CSV and, when supported by its columns, an energy/time summary.

For over-time sampling, interval_us is in microseconds: 10000 is 10 ms and 1000000 is 1 second. It sets the target pause between sampling cycles, not a guaranteed period; backend reads and scheduling add time. Window energy is reported per interval, not as instantaneous power. Sampling has a finite capacity of 262,144 rows.

Temperature baseline

When a CPU backend is active, all measurement and calibration modes require a readable CPU temperature from it; an unavailable or invalid reading stops execution before the workload. If only a GPU backend is active, temperature checks and calibration are skipped. If the baseline file is missing, a measurement creates it after the configured settling time.

[measurement]
mode = "temperature-calibration"
sleep_seconds = 10
calibration_file = "temperature.txt"

In measurements, variance controls how far above the baseline the CPU can be before a run starts. Standard checks before every repetition and records that pre-run temperature. Over-time mode checks before each run (after applying its powercap) and continues sampling temperature during execution. Relative output and baseline paths resolve from the working directory where the executable runs.

Powercap & calibration

Hardware state

Powercap controls can change real package limits. The Intel backend attempts to restore previous limits and zone state after each applied cap and reports restoration errors. Restoration has not been verified on all hardware; inspect RAPL state after every run, especially after an abrupt termination.

powercap = -1 leaves existing limits unchanged. A calibration baseline labelled -1 therefore uses the limits already in force; it is not necessarily uncapped. The backend attempts restoration after each applied value. Firmware or other controls may impose additional limits.

for file in /sys/class/powercap/intel-rapl:0/{enabled,constraint_0_power_limit_uw,constraint_1_power_limit_uw}; do
    echo "$file: $(cat "$file")"
done

This reads package 0 only; a multi-package host may expose additional zones. Values are in microwatts. Only use power limits supported by your hardware and account for permissions and external power-management software.

TOML fields

A configuration has a [measurement] table. Measurement modes also use [metrics] to choose CSV columns. Unknown keys and mode-incompatible settings are rejected, so keep each example's fields with its mode.

KeyModesMeaning, units and defaults
modeAllRequired. "standard", "overtime", "temperature-calibration" or "powercap-calibration".
commandStandard, over-time, powercap calibrationRequired foreground shell command to execute. Powercap calibration runs it for each repetition and cap.
language, programMeasurements and powercap calibrationOptional CSV labels, not selectors; defaults to "C" and "Target" in standard mode. Use simple labels without commas or quotes.
outputMeasurements and powercap calibrationCSV path; defaults to measurements.csv (standard), measurements_ot.csv (overtime), or powercap_calibration.csv. Relative to the directory where the executable runs.
repetitionsStandard, powercap calibrationNumber of workload runs per cap; positive integer. Defaults to 1 (standard) and 3 (powercap calibration).
timeout_hoursStandard, powercap calibrationMaximum duration of each workload run in hours; positive integer, default 1.
interval_usOver-time onlyTarget pause between sample cycles in microseconds; integer from 1 to 4,294,967,295. Default 1,000 µs (1 ms). Actual intervals are longer because reads and scheduling take time.
varianceMeasurements and powercap calibrationNon-negative temperature allowance in °C above the baseline before starting a workload. Defaults: 0°C in standard, 5°C in over-time mode and powercap calibration.
sleep_secondsAll modesNon-negative settling delay before creating a missing temperature baseline; also the delay for temperature calibration. Defaults: 5 seconds for measurements, 10 for powercap calibration and 20 for temperature calibration.
calibration_fileAll modesPath to the CPU-temperature baseline text file; defaults to /tmp/cores_temperatures.txt. If missing, a baseline is created after sleep_seconds.
powercapStandard, over-timeOne Watt limit or a list, e.g. [-1, 15, 20]; defaults to -1. Values must be -1 or positive integers; at most 128 unique values. -1 leaves existing limits unchanged. The backend attempts to restore applied limits after each cap's measurement.
powercap_min, powercap_maxPowercap calibration onlyRequired positive integer Watt limits. The range is inclusive and must contain fewer than 128 values. Calibration automatically includes an existing-limits baseline labelled -1.
compile_commandPowercap calibration onlyOptional shell command run once before measurements, useful for compiling the workload.
[metrics] selectStandard, over-time, powercap calibrationRequired non-empty list of metric names, or "all". Calibration defaults to ["cpu.Package"] if the table is omitted.

Standard: repeated measurements

[measurement]
mode = "standard"
command = "python3 workload.py --size 1000"
language = "Python"
program = "workload-1000"
output = "standard.csv"
repetitions = 5
timeout_hours = 1
variance = 5
sleep_seconds = 10
calibration_file = "temperature.txt"
powercap = [-1, 15, 20]

[metrics]
select = ["system.cores", "system.memory", "cpu.Package", "cpu.Temperature"]

This creates one CSV row for every repetition at every cap (15 rows in this example). It waits until CPU temperature is no higher than the calibrated baseline plus variance before each run. Each row includes the run duration and selected, available metrics; see the metric catalogue for names and units. The baseline value -1 does not remove any system power limits.

Over-time: samples during one run

[measurement]
mode = "overtime"
command = "python3 workload.py --size 100000"
language = "Python"
program = "long-workload"
output = "overtime.csv"
interval_us = 1000000
variance = 5
sleep_seconds = 10
calibration_file = "temperature.txt"
powercap = 15

[metrics]
select = ["system.workload_processes", "system.memory",
          "cpu.Package", "cpu.Temperature"]

This creates one CSV row per sampling cycle while the command runs. Here, interval_us = 1000000 requests roughly one-second cycles. Temperature is checked after the cap is applied and before the workload starts; subsequent temperature values are sampled during execution. The CSV's Timestamp_ms is elapsed time, and window-energy values cover the interval between samples.

Temperature baseline calibration

[measurement]
mode = "temperature-calibration"
sleep_seconds = 20
calibration_file = "temperature.txt"

Run python3 scripts/generate_config.py temperature.toml. This mode does not generate an executable or CSV; it waits, writes an lm-sensors snapshot and appends the measured average temperature to temperature.txt.

Powercap calibration: compare Watt limits

[measurement]
mode = "powercap-calibration"
command = "python3 workload.py"
compile_command = "make workload"
language = "Python"
program = "workload"
output = "powercap.csv"
powercap_min = 10
powercap_max = 20
repetitions = 3
timeout_hours = 1
variance = 5
sleep_seconds = 10
calibration_file = "temperature.txt"

[metrics]
select = ["cpu.Package"]

This produces a calibration CSV with 3 existing-limits baseline runs (Powercap = -1) and 3 runs for each integer cap from 10 through 20 W. When the CSV includes cpu.Package and Time_ms, GreenMeasurer also invokes the bundled post-processor for an energy/time comparison. Powercap changes affect real hardware and may require elevated permissions; inspect the current limits before and after a run.

Selecting metrics and adapters

Use names listed by ./src/main --list-metrics. System metrics use system.*; backend metrics use cpu.* or gpu.*. select = "all" includes all available metrics, so CSV columns can vary by hardware. Metric names and units are documented in the catalogue.

Existing compiled metric adapters can be named in [[adapters]] tables and selected as external.<name>.<metric>:

[metrics]
select = ["system.cores", "external.demo.RunningProcesses"]

[[adapters]]
name = "demo"
path = "build/libdemo-metrics.so"

For a simple C function, [[external_metrics]] asks the generator to compile an adapter. Required fields are name, metric, unit, function, header, sources and return_type. Paths are relative to the TOML file. The function's declared return type and argument types must match its C header:

[measurement]
mode = "overtime"
command = "sleep 1"
output = "external-metric.csv"
interval_us = 10000

[metrics]
select = ["external.processes.RunningProcesses"]

[[external_metrics]]
name = "processes"
metric = "RunningProcesses"
unit = "count"
function = "get_number_of_running_processes"
header = "src/tests/fixtures/custom_metric/processes.h"
sources = ["src/tests/fixtures/custom_metric/processes.c"]
return_type = "int"
arguments = []
error_value = -1

return_type and argument type may be "int", "unsigned int" or "double". arguments is optional (empty by default); each entry has a type and numeric value, for example arguments = [{ type = "int", value = 5 }, { type = "double", value = 1.5 }]. Optional error_value marks a return value as a failed reading. Optional include_dirs and libraries add C include directories and library names (without -l) to the build. The generator creates the configured executable and adapter files in the output directory; the selected external value is added as a CSV column. See the custom metric fixture for a complete example.

Use python3 scripts/validate_config.py path/to/config.toml to check a file before generation. Generate an executable with ./src/main --config path/to/file.toml --directory build-dir, then run ./build-dir/greenmeasurer. Generation compiles the configuration but does not execute the workload. Output and baseline paths resolve from the run's working directory; adapter, header and source paths resolve from the TOML's directory. Create any parent directories needed by your output paths before running.

When a metric is missing

Run ./src/main --list-metrics to inspect compiled plugins. To see runtime detection details, run a generated executable with GREENMEASURER_VERBOSE_BACKENDS=1. Check backend build dependencies, hardware support and permissions.

Intel integrated GPUs are detected from PCI device information, independently of MSR permissions. The Intel GPU backend may therefore be reported as selected even when GPU energy readings are unavailable: its RAPL counter still requires access to the MSR device. GPU temperature readings also depend on a supported sensor being present.

Metrics unavailable at preflight are skipped with a warning; readings that fail later are recorded as NOT_SUPPORTED. CPU package energy includes other activity in the same hardware domain. It is not process-exclusive, and overlapping domains should not be added together.
